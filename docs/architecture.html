Phase 1 — Analyse & architecture

LubriManager : architecture d'un système transactionnel de cartes clients

Application desktop Windows pour la vente et la distribution de lubrifiants — gestion des clients, cartes, comptes prépayés, produits, stock et transactions, avec traçabilité intégrale et intégrité financière garantie.

01Résumé exécutif & périmètre

Ce document est le livrable de la Phase 1. Il ne contient pas de code applicatif : il fixe l'architecture, le modèle de données, les règles métier et la liste des décisions à valider avant le démarrage de la Phase 2 (authentification).

Nature du système

LubriManager n'est pas un CRUD. C'est un registre transactionnel financier : chaque mouvement d'argent ou de stock est un fait immuable, horodaté, attribué à un utilisateur et réconciliable. Le solde d'un compte n'est jamais « modifié » — il est la projection d'une suite d'écritures. Trois propriétés priment sur toute autre considération :

  1. Intégrité financière — atomicité des opérations, aucun solde ni stock partiellement écrit, idempotence des opérations sensibles.
  2. Traçabilité — toute opération importante laisse une trace d'audit ; aucune transaction validée n'est supprimée, seulement contre-passée.
  3. Contrôle d'accès — les permissions sont vérifiées côté serveur, jamais dans React.

Principe d'architecture directeur

Le backend Spring Boot est le cœur métier et l'unique source de vérité. React/Tauri est un client léger : il affiche, saisit, valide de façon ergonomique, mais ne décide rien. Toute règle (solde suffisant, unicité de carte, droit d'annuler) est appliquée et re-vérifiée par l'API. Cette séparation permet d'ajouter plus tard une application mobile ou un tableau de bord web sur le même backend, sans réécriture.

03Architecture générale

Trois niveaux, un seul contrat : l'API REST HTTPS documentée en OpenAPI. Le poste de travail n'ouvre jamais de connexion directe à PostgreSQL.

Principes directeurs

  • Backend headless — aucune dépendance à un client particulier ; le desktop est un consommateur parmi d'autres à venir.
  • Stateless — l'API ne garde pas de session serveur ; l'état d'authentification tient dans le JWT. Montée en charge horizontale possible.
  • Contrat d'abord — OpenAPI publié par le backend ; le front génère ses types TypeScript à partir du schéma (pas de dérive de contrat).
  • Fail closed — en cas de doute (permission, solde, connectivité), l'opération est refusée, jamais tentée « au mieux ».

04Architecture backend Spring Boot

Découpage en couches

Quatre couches, une seule direction de dépendance (de haut en bas). La logique métier vit dans les services, jamais dans les contrôleurs.

Un package racine par domaine métier ; chaque package est autonome (controller/service/repository/entity/dto/mapper/exception). Découpage possible en modules Maven plus tard sans refactor.

Éléments transverses

  • @RestControllerAdvice global — traduit toute exception en ApiError normalisé (voir §17), journalise la stacktrace côté serveur, expose un message intelligible côté client.
  • Générateur de références — service dédié s'appuyant sur une table reference_counter (préfixe, date, séquence) verrouillée, garantissant RECH-20260903-000001 strictement croissant et sans trou exploitable.
  • Horloge injectable (java.time.Clock) — pour des tests déterministes des horodatages.
  • Publication d'événements (ApplicationEventPublisher) — audit et notifications sont abonnés, sans coupler le service métier.

05Architecture frontend React

Organisation par fonctionnalité

Le code est regroupé par domaine dans features/ (chaque feature : composants, hooks, appels API, types, routes). Le générique reste dans components/, lib/, hooks/.

Couche données

  • Client HTTP — instance Axios unique : base URL, intercepteur qui ajoute Authorization: Bearer, intercepteur 401 → tentative de refresh puis rejeu, sinon déconnexion.
  • TanStack Query — un hook par ressource (useCustomers, useCard(id)…). Les mutations financières passent une Idempotency-Key (UUID généré au montage du formulaire, figé jusqu'au succès) et invalident les caches impactés.
  • Types partagés — générés depuis openapi.json du backend (script npm run gen:api). Le front ne redéclare jamais un DTO à la main.

État applicatif

  • Auth — store Zustand : utilisateur courant, rôles, access token en mémoire. Persistance du seul refresh token, côté Tauri (keychain).
  • UI — préférences locales (thème, densité des tableaux, dernier filtre) dans localStorage, en lecture défensive.

Routing & garde

React Router avec routes protégées : un <RequireAuth roles={[…]}> masque l'UI non autorisée — confort seulement. L'autorisation réelle est celle du backend ; le front doit gérer proprement un 403 renvoyé malgré une UI affichée.

Qualité

  • Formulaires : Mantine Form + résolveur Zod (mêmes règles de validation que Bean Validation, dupliquées volontairement pour l'ergonomie).
  • Composants transverses : DataTable paginée serveur, MoneyInput (FCFA, séparateur de milliers), StatusBadge, ConfirmDialog, ReceiptPrint.
  • Formatage centralisé : formatMoney, formatDate/formatTime (locale fr, fuseau Lomé).

07Modèle de données

Modèle relationnel normalisé. Séparation nette Client → Compte → Solde et Carte : la carte est un moyen d'accès, pas le portefeuille. Perdre une carte n'affecte ni le compte ni l'historique.

DEC-01 — bloquant

Cardinalité compte. Un client possède-t-il exactement un compte, ou plusieurs (ex. par site, par famille de produits) ?

Recommandation : 1 client = 1 compte en v1, N cartes pointant vers ce compte. Le multi-comptes est une évolution ; le schéma garde account.customer_id non-unique techniquement mais contraint applicativement, pour ne pas bloquer l'évolution.

DEC-02

Multi-agences. Le cahier des charges cite « plusieurs agences » en évolution. Introduire dès maintenant une colonne branch_id (avec une agence par défaut) évite une migration lourde plus tard.

Recommandation : ajouter branch_id dès la Phase 1 sur user, card, transaction, inventory_movement, valorisé à l'agence unique. Coût quasi nul, gain élevé.

Validation des opérations sensibles. Quelles opérations exigent l'aval d'un MANAGER, et selon quel seuil (montant) ? Le workflow est-il bloquant (l'agent attend) ou asynchrone (opération en EN_ATTENTE, effet différé) ?

12Flux de recharge

// recharge/RechargeService.java — cœur de la logique
@Transactional
public RechargeResult recharge(RechargeCommand cmd, String idemKey, UserRef actor) {

  // RG-09 : garde d'idempotence
  var replay = idempotency.find(idemKey);
  if (replay.isPresent()) return replay.get().as(RechargeResult.class);

  // DEC-01 : un compte par client — verrou pessimiste
  Account acc = accountRepo.lockByCardNo(cmd.cardNo())       // SELECT ... FOR UPDATE
      .orElseThrow(() -> new NotFoundException("Carte introuvable"));
  Card card = acc.cardByNo(cmd.cardNo());

  // RG-02 / RG-03 / RG-04
  require(card.status() == ACTIVE,        "Carte non active");
  require(acc.customer().status() == ACTIF, "Client non actif");
  require(cmd.amount().signum() > 0 && cmd.amount().compareTo(maxRecharge()) <= 0,
                                         "Montant invalide");

  Money before = acc.balance();
  Money after  = before.plus(cmd.amount());
  boolean pending = cmd.amount().compareTo(approvalThreshold()) > 0;  // DEC-03

  Transaction txn = Transaction.recharge(acc, card, actor, cmd.amount(),
      before, after, pending ? EN_ATTENTE : VALIDEE,
      references.next("RECH"), idemKey);

  if (!pending) acc.setBalance(after);          // RG-16 · invariant RG-00

  Recharge rec = Recharge.of(txn, cmd.paymentMethodId(), cmd.comment(), actor);
  txnRepo.save(txn); rechargeRepo.save(rec);

  audit.record(RECHARGE, actor, acc, before, after);
  var result = RechargeResult.from(txn, rec);
  idempotency.store(idemKey, "/api/recharges", cmd.hash(), result);
  events.publish(new RechargeCompleted(txn.id(), pending));
  return result;
  // toute exception ⇒ rollback total : rien n'est écrit
}

13Flux de vente

La vente est l'opération multi-ressources critique : elle touche compte, transaction, stock et mouvements de stock. Les quatre écritures réussissent ou échouent ensemble.

DEC-04 — bloquant

TVA / fiscalité. Les prix produits sont-ils TTC ou HT ? La TVA (18 % au Togo) doit-elle apparaître sur la facture ? Un numéro de facture normalisée / conformité fiscale est-il requis ?

Recommandation : trancher avant la Phase 6. Par défaut : prix TTC, champ tax calculé et affiché pour information, séquence de facture distincte de la référence de vente si la conformité l'exige.

DEC-05

Trace des ventes refusées. Un refus pour solde insuffisant crée-t-il une transaction de statut REFUSEE, ou seulement une entrée d'audit ?

Recommandation : audit seul (action ACHAT_REFUSE) écrit dans une transaction BD indépendante. Le grand livre ne contient que des écritures VALIDEE/ANNULEE. Un rapport « tentatives refusées » est alimenté par l'audit.

14Flux d'annulation / contre-passation

Aucune suppression physique. Une correction crée une écriture inverse liée à l'originale, qui reste visible et passe au statut ANNULEE.

Règle d'or n°2 — intégrité

Le solde n'est jamais « remis à la main ». Il ne bouge que par une transaction VALIDEE. Une erreur se corrige par une nouvelle écriture, jamais par un UPDATE ou un DELETE sur l'historique.

DEC-06

Annulation partielle. Autorise-t-on l'annulation d'une seule ligne de vente, ou uniquement l'annulation totale d'une transaction ?

Recommandation : annulation totale uniquement en v1 ; ré-effectuer une vente corrigée si besoin. L'annulation partielle multiplie les cas limites (stock, arrondis, TVA).

DEC-07

REMBOURSEMENT vs ANNULATION. Le type REMBOURSEMENT (§21 du cahier) désigne-t-il un retour d'argent hors caisse (espèces rendues), distinct de la contre-passation comptable ?

Recommandation : ANNULATION = correction d'erreur (recrédite le compte) ; REMBOURSEMENT = sortie de valeur du compte vers un moyen de paiement (client quitte le système). À confirmer.

15Stratégie d'intégrité financière

Atomicité

  • Une opération = une méthode @Transactional unique. Débit + transaction + stock + mouvement dans la même unité de travail.
  • Toute exception (métier ou technique) ⇒ ROLLBACK complet. Aucune écriture partielle.
  • Isolation READ COMMITTED (défaut PostgreSQL) + verrous explicites là où il faut.

Concurrence

  • Verrou pessimiste SELECT … FOR UPDATE sur la ligne account pour toute écriture de solde.
  • Verrou des produits d'une vente triés par id — ordre déterministe, pas d'inter-blocage.
  • @Version sur account comme filet de sécurité (détecte une modification concurrente non verrouillée).

Idempotence (RG-09)

  • En-tête Idempotency-Key (UUID) obligatoire sur recharge, vente, annulation.
  • Contrainte UNIQUE sur idempotency_record.key : la 2ᵉ tentative échoue à l'insert et renvoie le résultat mémorisé.
  • Le hash de la requête est comparé : même clé + charge différente ⇒ 409.

Cohérence du solde

  • Invariant RG-00 : balance == Σ(transactions VALIDEE).
  • Job de réconciliation nocturne : recalcul par compte, alerte CRITIQUE en cas d'écart, blocage optionnel du compte.
  • balance_before/balance_after sur chaque écriture ⇒ rejouabilité du grand livre.
Garde-fous base de données

CHECK (balance >= 0) · CHECK (balance = trunc(balance)) · CHECK (stock_qty >= 0) · UNIQUE(card_no) · UNIQUE(transaction.reference) · UNIQUE(idempotency_record.key) · FK en RESTRICT. La base refuse une incohérence même si un bug applicatif la laisse passer.

DEC-08

Découvert autorisé. Un client « de confiance » peut-il passer temporairement en solde négatif (plafond de crédit) ? Le cahier des charges impose le refus par défaut.

Recommandation : aucun découvert en v1 (CHECK balance >= 0). Si un crédit client est souhaité, le modéliser explicitement plus tard (champ credit_limit), pas par un solde négatif silencieux.

16Audit & traçabilité

Deux niveaux complémentaires :

  1. Grand livre (transaction, inventory_movement) — la vérité métier, en ajout seul, avec référence, auteur, soldes/stocks avant-après.
  2. Piste d'audit (audit_log) — le « qui a fait quoi, quand, depuis où » sur toute action importante, y compris les consultations sensibles et les échecs.

Recommandation : audit conservé ≥ 5 ans en ligne (obligations comptables), notifications purgées après 12 mois. À confirmer avec le comptable de l'entreprise.

17Stratégie de sécurité

Authentification

  • Spring Security + filtre JWT sans état. POST /api/auth/login renvoie un access token court (≈ 15 min) et un refresh token long (≈ 7 j, DEC-15).
  • Rotation du refresh token à chaque /refresh ; l'ancien est révoqué (refresh_token.revoked_at). Détection de rejeu ⇒ révocation de toute la famille.
  • Stockage poste : access token en mémoire React ; refresh token chiffré via keychain OS (Tauri). Jamais dans localStorage.
  • POST /api/auth/logout révoque le refresh token courant.
  • Mots de passe : BCrypt (coût 12). Politique de complexité + verrouillage après N échecs — DEC-14.

Autorisation (RBAC)

  • Filtrage d'URL par rôle et @PreAuthorize au niveau des méthodes de service — double barrière.
  • Le rôle vient du token, re-vérifié à chaque requête ; un token d'un utilisateur désactivé est rejeté (RG-17).
  • Aucune décision d'autorisation n'est déléguée au front (§10).

22Déploiement, sauvegarde & mode hors-ligne

Topologie

CI / CD

  • CI : build + tests (Testcontainers) + analyse dépendances + lint, à chaque PR.
  • Backend : artefact .jar exécutable (ou image conteneur) ; migrations Flyway au démarrage ; profils dev/prod.
  • Desktop : tauri build → LubriManager-Setup.exe (NSIS) signé ; publication sur l'endpoint de l'updater.

Sauvegarde PostgreSQL

  • pg_dump chiffré quotidien + archivage WAL continu (PITR possible).
  • Rétention : 7 quotidiennes, 4 hebdomadaires, 6 mensuelles. Copie hors-site.
  • Restauration testée trimestriellement (procédure documentée dans docs/).
  • Sauvegarde manuelle déclenchable depuis l'écran Paramètres (ADMIN).

Mode hors-ligne — architecture recommandée

Il s'agit d'argent et de stock partagés entre postes. Une file d'opérations financières purement locale exposerait à : double débit (même carte servie hors-ligne sur deux postes), sur-vente de stock, soldes divergents à la resynchronisation. Ces risques ne sont pas maîtrisables proprement en v1.

Recommandation — online-first

v1 : les opérations financières (recharge, vente, annulation, ajustement) exigent la connexion au serveur. Hors-ligne, l'application reste ouverte en lecture seule (cache TanStack Query persistant : fiches clients, cartes, catalogue, derniers soldes connus marqués « non temps réel ») et les boutons d'action financière sont désactivés avec un message explicite. Rien n'est mis en file.

Si un vrai mode déconnecté devient indispensable (évolution) : l'architecture le permet sans casse grâce à des fondations déjà posées —

  • références et clés d'idempotence générées côté serveur ⇒ une opération mise en file obtient sa clé à la reconnexion, le serveur reste juge de l'unicité ;
  • le serveur reste l'autorité du solde : une opération hors-ligne est une demande revalidée à la synchronisation (solde recalculé, refus possible → notification à l'agent) ;
  • file locale chiffrée, ordonnancée, avec statut par opération (EN_ATTENTE_SYNC → VALIDEE/REJETEE) ;
  • plafond hors-ligne par poste et par carte, borné par app_setting ;
  • résolution de conflit déterministe : la première opération serveur gagne, les suivantes sont rejetées et remontées à l'agent.
DEC-17 — bloquant

Hébergement & connectivité. Le serveur Spring Boot / PostgreSQL est-il sur une machine du réseau local de l'entreprise, ou sur un VPS distant ? La connexion inter-postes est-elle fiable (LAN) ou dépendante d'Internet ? Cette réponse conditionne l'urgence réelle du mode hors-ligne et le type de certificat TLS.

Recommandation : serveur sur machine dédiée du LAN de l'agence, postes en réseau câblé/Wi-Fi local ⇒ le online-first suffit largement en v1.
